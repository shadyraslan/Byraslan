## نظرة عامة على النظام

نظام **باي رسلان ERP** هو نظام تخطيط موارد المؤسسات (ERP) مصمم لإدارة عمليات ثلاث علامات تجارية:
- **روستوز** (منتجات ألبان)
- **رسلان ماركت**
- **أوريتشي**

النظام يغطي كامل سلسلة العمليات من الإنتاج إلى البيع:
- إدارة المصنع وأقسامه (أوامر الإنتاج، التغليف، تتبع الغرف)
- إدارة المخزون (تحويلات، هالك، تبرعات، تتبع العلب)
- المشتريات (أوامر توريد، استلام، كارت الصنف، التجاوزات)
- البيع (نقاط بيع POS، طلبات أونلاين، فواتير، ورديات)
- الحسابات (ملخص يومي، مصروفات، حسابات الموردين)
- إدارة الفروع والمواقع
- إدارة المستخدمين والصلاحيات

## تحليل الوحدات والمكونات

### 1. وحدة المصادقة (Authentication)

**الملفات:** `login/page.tsx`, `login/login-action.ts`, `rate-limit.ts`, `password-policy.ts`

- تسجيل دخول بالإيميل أو رقم الموبايل
- تحويل أرقام الموبايل لإيميلات داخلية (`@staff.byraslan.app`)
- حماية من الهجمات بالقوة الغاشمة (Rate Limiting: 5 محاولات / 15 دقيقة)
- رسائل خطأ عامة لا تكشف صحة الإيميل أو كلمة المرور
- سياسة كلمة مرور قوية (8 أحرف + حرف كبير + حرف صغير + رقم)
- إعادة تعيين كلمة المرور عبر رابط آمن (token)

### 2. وحدة الصلاحيات (Authorization)

**الملفات:** `perms.ts`, `roles.ts`, `users/page.tsx`, `users/actions.ts`, `users/staff.ts`

- نظام صلاحيات مرن جداً (RBAC + ABAC)
- 27 صلاحية موزعة على 8 مجموعات
- 8 أدوار جاهزة (قوالب)
- الصلاحيات يمكن منحها:
  - لمدة محددة (تاريخ انتهاء)
  - بحد مبلغ أقصى
  - مع تتبع من منّحها
- المالك (is_owner) لديه كل الصلاحيات تلقائياً
- الموظف غير النشط (active=false) لا يمكنه الدخول
- التحقق من الصلاحيات يتم على مستويين:
  - **Frontend:** `can(me, perm)` — إخفاء الأزرار والروابط
  - **Backend:** RLS policies + `has_perm()` في PostgreSQL

### 3. وحدة المخزون (Stock)

**الملفات:** `stock/page.tsx`, `stock/dispose/`, `transfers/`, `boxes/`, `crates/`

- نظام دفتر حركات (stock_moves) — كل حركة مسجلة
- تتبع العلب برقم مميز (serial number)
- QR Code لكل علبة
- تحويلات بين المواقع بالمسح
- تتبع حالة كل علبة (stock → transit → sold/waste/donated)
- هالك وتبرعات بصلاحيات منفصلة
- ملصقات الصناديق البلاستيك

### 4. وحدة الإنتاج (Production)

**الملفات:** `production/`, `station/`, `pack/`

- أوامر إنتاج مع خطوات متعددة (مشوار على الغرف)
- كل غرفة لها تابلت خاص
- تتبع الوزن الداخل والخارج والهالك في كل خطوة
- محطة تغليف مع ميزان وطباعة QR
- أوامر تغليف جاهزة (pack_ready)

### 5. وحدة المشتريات (Purchasing)

**الملفات:** `purchasing/`, `overrides/`

- أوامر توريد (Purchase Orders)

### نظام RLS (Row Level Security)

كل الجداول محمية بـ RLS مع سياسات محددة:
- `profiles`: القراءة للجميع، الكتابة للمدير فقط
- `grants`: القراءة للمستخدم نفسه أو المدير
- `locations`: القراءة للجميع، الكتابة لـ `stock.edit`
- `settings`: القراءة للجميع، الكتابة لـ `settings.edit`
- `audit_log`: القراءة لـ `audit.view` فقط

## تحليل الأمان

### ✅ نقاط القوة

1. **Security Headers في Middleware:**
   - `X-Content-Type-Options: nosniff`
   - `X-Frame-Options: DENY`
   - `X-XSS-Protection: 1; mode=block`
   - `Referrer-Policy: strict-origin-when-cross-origin`
   - `Permissions-Policy: camera=(), microphone=(), geolocation=()`
   - `Strict-Transport-Security` (في الإنتاج)

2. **Rate Limiting:**
   - على مستوى التطبيق: 5 محاولات دخول / 15 دقيقة
   - على مستوى قاعدة البيانات: 10 طلبات أونلاين / ساعة لكل عميل

3. **حماية كلمات المرور:**
   - سياسة قوية (8 أحرف + كبير + صغير + رقم)
   - رسائل خطأ عامة لا تكشف صحة البيانات
   - إعادة تعيين عبر token آمن

4. **RLS (Row Level Security):**
   - كل الجداول محمية
   - الصلاحيات تتحقق في قاعدة البيانات (ليس فقط في الواجهة)

5. **Service Role Key:**
   - مخزن في Vercel Environment Variables فقط
   - لا يصل للمتصفح أبداً

6. **Audit Log:**
   - تسجيل جميع التعديلات على grants, locations, settings

7. **قفل الصفوف (Row Locking):**
   - في `pos_sale` لمنع بيع نفس العلبة مرتين (race condition)

8. **حماية الموظفين:**
   - الموظف غير النشط لا يمكنه الدخول
   - المالك لا يمكن إيقاف حسابه من نفسه

### ⚠️ نقاط ضعف محتملة

1. **Rate Limiting في الذاكرة (In-Memory):**
   - `rate-limit.ts` يستخدم `Map` في الذاكرة
   - **المشكلة:** لا يعمل مع عدة instances (Vercel scales horizontally)
   - **الحل:** Rate Limiting في قاعدة البيانات موجود (0026) لكن Rate Limiting تسجيل الدخول لا يزال in-memory

2. **لا يوجد Content Security Policy (CSP):**
   - مفقود من Security Headers

3. **لا يوجد CSRF Protection صريح:**
   - Next.js يوفر حماية CSRF بشكل افتراضي، لكن لا يوجد تأكيد

4. **لا يوجد Rate Limiting على Server Actions:**
   - بعض الـ actions (مثل `grant`, `revoke`) قد تُستغل

5. **لا يوجد تسجيل نشاط المستخدمين (User Activity Logging):**
   - Audit Log يغطي grants, locations, settings فقط
   - لا يغطي العمليات الحرجة (بيع، تحويل، هالك)

6. **لا يوجد Multi-Factor Authentication (MFA):**
   - Supabase يدعم MFA لكن غير مفعّل

7. **لا يوجد Session Timeout:**
   - الجلسة تبقى مفتوحة حتى خروج المستخدم يدوياً

8. **لا يوجد IP Whitelisting:**
   - قد يكون مفيداً للوصول من الفروع فقط

## الأخطاء والمشاكل المكتشفة

### 🔴 مشاكل حرجة

**P1-1: Rate Limiting تسجيل الدخول لا يعمل مع عدة Instances**
- **الملف:** `lib/rate-limit.ts`
- **المشكلة:** يستخدم `Map` في الذاكرة. Vercel يشتغل على عدة instances. لو المستخدم حاول من instance مختلف، الـ rate limit مش هيعمل.
- **التأثير:** هجوم بالقوة الغاشمة ممكن يتخطى الحماية
- **الحل:** نقل Rate Limiting تسجيل الدخول لقاعدة البيانات (مثل `hit_rate_limit`)

**P1-2: لا يوجد Content Security Policy (CSP)**
- **الملف:** `middleware.ts`
- **المشكلة:** مفقود من Security Headers
- **التأثير:** هجوم XSS ممكن ينفذ سكربتات خارجية
- **الحل:** إضافة `Content-Security-Policy` header

**P1-3: لا يوجد Session Timeout**
- **المشكلة:** الجلسة تبقى مفتوحة إلى الأبد
- **التأثير:** لو جهاز مشترك، أي حد يقدر يدخل
- **الحل:** إضافة session expiry (مثلاً 8 ساعات)

### 🟡 مشاكل متوسطة

**P2-1: Audit Log غير شامل**
- **المشكلة:** يغطي grants, locations, settings فقط
- **التأثير:** مفيش سجل للعمليات الحرجة (بيع، تحويل، هالك)
- **الحل:** إضافة triggers على sales, stock_moves, transfers

**P2-2: لا يوجد Rate Limiting على Server Actions**
- **المشكلة:** actions مثل `grant`, `revoke`, `createStaff` مش محمية
- **التأثير:** ممكن يتم استغلالها برمجياً
- **الحل:** إضافة rate limiting على actions الحرجة

**P2-3: عدم وجود Multi-Factor Authentication**
- **المشكلة:** مصادقة بعامل واحد فقط
- **التأثير:** لو كلمة المرور مسروقة، الحساب معرض للخطر
- **الحل:** تفعيل MFA في Supabase (خاصة للمالك)

**P2-4: صفحة `/order` (العميل) بدون Rate Limiting على مستوى التطبيق**
- **المشكلة:** Rate Limiting موجود في DB فقط (10 طلبات/ساعة)
- **التأثير:** العميل ممكن يحاول بسرعة قبل ما الـ trigger يعمل
- **الحل:** إضافة تحقق في الـ Server Action

**P2-5: `searchParams` بدون معالجة أخطاء في بعض الصفحات**
- **الملف:** `items/page.tsx` (سطر 15)
- **المشكلة:** `q.replace(/[{},#]/g, "")` — لو `q` يحتوي أحرف خاصة في SQL، ممكن يسبب مشكلة
- **التأثير:** SQL Injection محتمل (رغم أن Supabase يحمي بشكل عام)
- **الحل:** استخدام parameterized queries بشكل صارم

**P2-6: لا يوجد Error Boundary**
- **المشكلة:** لو مكون React فشل، الصفحة كلها بتتوقف
- **التأثير:** تجربة مستخدم سيئة
- **الحل:** إضافة Error Boundaries في layout

**P2-7: عدم وجود Loading States**
- **المشكلة:** الصفحات بتظهر فارغة أثناء التحميل
- **التأثير:** المستخدم مش عارف لو النظام شغال ولا لا
- **الحل:** إضافة loading.tsx في كل صفحة

**P2-8: عدم وجود Not Found Pages**
